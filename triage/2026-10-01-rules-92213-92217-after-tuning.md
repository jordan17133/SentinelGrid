## Summary

Rule 100100 removed the scheduled-watchdog noise from rule 92213, but the SOC Overview still showed new Critical alerts. Page 1 says "Critical means investigate," so every one of the 51 was traced to the process that caused it. They fall into three clusters: the AMD Bug Report Tool unpacking itself after graphics driver crashes, PowerShell compiling code into Temp for the AI coding assistant used to build this lab, and one Windows troubleshooter. Rule 92217 (Low) was reviewed at the same time: all 577 alerts are software installs and updates. None of the activity is malicious. The AMD cluster pointed to a real stability problem on the host.

### A. AMD Bug Report Tool, 2026-10-01 06:03 to 06:05 UTC (2:03 to 2:05 AM local)

1. **Binary:** `Get-AuthenticodeSignature` reports **Valid**, signed by `CN=Advanced Micro Devices, O=Advanced Micro Devices`. Version 1.7.0.0, product "AMD Bug Report Tool", SHA-256 `E9B969114FD213C696F96B6078C275F17B1F20C748CDCC125CD308B8A9B9BA51`. It sits in `SysWOW64`, which needs administrator rights to write.
2. **What triggered it:** the Windows Application log shows a burst of `LiveKernelEvent` reports from 02:03:48 to 02:05:16 local. Code 117 is a display driver timeout that Windows recovered from; codes 193 and 1b0 are graphics-kernel live dumps. At 02:04:07, `ApplicationFrameHost.exe` crashed inside `amdxx64.dll`, an AMD driver module.
3. **The process tree around it** (Sysmon process alerts in the warehouse): Radeon Software restarted its own services (`cncmd.exe restart`, `RSServCmd.exe restart`, `AMDRSServ.exe`) and queried hardware details, all from `C:\Program Files\AMD\`. The bug report tool unpacked its payload each time the driver recovered, and `AWSSDK.S3.dll` is what it uses to upload crash reports to AMD.
4. **What happened next:** the user restarted the PC from the Start menu at 02:06:56 (System log event 1074), shortly after a Defender offline scan reboot at 00:44.

**Verdict:** benign. The alert is worth having, though: it surfaced repeated GPU driver crashes that are otherwise easy to miss.

### B. PowerShell compiling code: 8 compiles, 17:32 to 21:13 UTC

1. Each compile follows the same steps: `powershell.exe` writes `<random>.cmdline` and `<random>.dll` to Temp, and then `csc.exe /noconfig /fullpaths @"...\<random>.cmdline"` compiles the DLL. This is how PowerShell's `Add-Type` builds a C# type at runtime.
2. **Parent:** for all 8 of 8 compiles, the parent PowerShell command line (rule 92006 and 92032 process alerts, joined on the Sysmon process GUID) starts with `$__claudeCodeScript`. That is the PowerShell tool of Claude Code, the AI coding assistant used to build this lab, which used `Add-Type` to call Windows APIs while automating Power BI Desktop. The times match those build sessions.
3. **Why it is Critical:** attackers use the same method (T1027.004, Compile After Delivery) to build payloads on the target so that no finished executable ever crosses the network.

**Verdict:** benign, authorized admin tooling. **Not tuned on purpose.** The only thing that sets it apart from an attack is the parent command line, and any process can fake that. Eight alerts across a full build day is an acceptable price for keeping this technique at Critical.

### C. Windows troubleshooter, 06:43 UTC

`sdiagnhost.exe` (the Scripted Diagnostics host behind Windows troubleshooters) started PowerShell, which wrote the same execution-policy test file that rule 100100 already handles for `powershell.exe`. It happened 38 minutes after the graphics driver crashes, which fits a troubleshooter running after the failure. **Verdict:** benign. One alert does not justify widening rule 100100.

Every alert lines up with a software install or update that was done on purpose or that Windows scheduled. The rule is already Low, which is the right level for this activity: it records software changes to system folders without paging anyone. **Verdict:** benign. No tuning needed.

## Recommendations

1. **Update or reinstall the AMD graphics driver.** Several display driver timeouts in two minutes, plus an app crash inside the driver, is a stability problem. If the crashes come back after the update, check GPU temperatures and Windows' Reliability Monitor.
2. **Keep 92213 at full severity for `csc.exe` and `Add-Type`.** Re-check the parent of every future compile alert. A parent that is not a known admin tool is worth escalating.
3. **Review 92217 by volume, not one alert at a time.** A burst of these with no matching install would be the signal to investigate.

## Verdict

Benign. All 51 Critical alerts after tuning, and all 577 alerts for rule 92217, are traced to a named, signed or expected process. The AMD crashes are a real host-health finding, now recorded.
